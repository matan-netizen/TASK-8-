# Manage: תפעול ותחזוקה

## 1. ניטור שוטף

| מה בודקים | איך | מה תקין |
|---|---|---|
| השרת עובד | פותחים `https://web-production-c4854.up.railway.app/api/health` | `"status": "ok"` |
| מצב ה-AI | אותו נתיב, השדה `checks.aiMode` | `anthropic` אם הוגדר מפתח, אחרת `demo` |
| מאגר המידע | אותו נתיב, השדה `checks.knowledge` | מספר המסמכים, ו-`isSample: false` כשמחובר מאגר אמיתי |
| גרסה | אותו נתיב, השדה `version` | 7 התווים הראשונים של ה-commit שרץ |
| יומנים | Railway: שירות web, לשונית Deployments, ואז View Logs | בלי שגיאות `[api]`, `[ai]`, `[knowledge]` |

**דוגמה לתשובה תקינה:**
```json
{
  "status": "ok",
  "version": "2a39fb0",
  "checks": {
    "aiMode": "demo",
    "storage": { "status": "ok", "tasks": 12 },
    "knowledge": { "status": "ok", "docs": 3, "isSample": true }
  }
}
```

נקודת התקינות ציבורית בכוונה, ולכן היא מחזירה רק מספרים וסטטוסים, אף פעם לא תוכן של משימות או מסמכים.

### מה מופיע ביומנים

| קידומת | משמעות | מה עושים |
|---|---|---|
| `[api] unexpected error` | שגיאה לא צפויה בשרת | בודקים את ההודעה. המשתמש ראה "אירעה שגיאה בשרת" |
| `[ai] ... using demo fallback` | הקריאה ל-Anthropic נכשלה, והמערכת עברה למצב הדגמה | בודקים שהמפתח תקין ושיש יתרה בחשבון Anthropic |
| `[knowledge] failed to read` | קובץ במאגר לא נקרא | פותחים את הקובץ ושומרים מחדש, או ממירים לפורמט נתמך |
| `[health] storage check failed` | בעיה בגישה לקובץ הנתונים | בודקים שה-Volume מחובר ושהמשתנה `DATA_DIR` נכון |

## 2. גיבוי ושחזור

כל הנתונים נמצאים בקובץ אחד: `/data/db/db.json` ב-Volume (מקומית: `./data/db.json`).

- **גיבוי:** אם תוכנית Railway שלך כוללת גיבויי Volume, מפעילים אותם בהגדרות ה-Volume. אחרת, ומקומית, מספיק להעתיק את הקובץ.
- **שחזור:** מחזירים את הקובץ למקומו ומפעילים את השירות מחדש.
- **איפוס כל הנתונים:** מוחקים את `db.json`, והמערכת תתחיל ריקה. זו פעולה בלתי הפיכה, אז מגבים קודם.

הכתיבה לקובץ אטומית (כתיבה לקובץ זמני ואז החלפה), כך שקריסה באמצע כתיבה לא משאירה קובץ פגום.

## 3. פעולות נפוצות

### הוספה או החלפה של מפתח AI
Railway: פרויקט task-8, שירות web, לשונית Variables, ואז מעדכנים את `ANTHROPIC_API_KEY`. השירות יעלה מחדש אוטומטית. אחרי זה בודקים ש-`/api/health` מראה `"aiMode": "anthropic"`.

### עדכון מסמכים במאגר (מקומית)
מוסיפים, מעדכנים או מוחקים קבצים בתיקייה `knowledge/`. המאגר נבנה מחדש אוטומטית בבקשה הבאה, בלי הפעלה מחדש.

### הוספת משתמש דמו
עורכים את `src/lib/users.ts`, מוסיפים שורה (מזהה, שם, תפקיד), ופותחים Pull Request.

### עדכון גרסה
כל שינוי נכנס דרך Pull Request ל-`main` (ראו סעיף 4). אחרי המיזוג Railway מעלה את הגרסה לבד. בסוף בודקים ש-`version` ב-`/api/health` השתנה.

## 4. תהליך העבודה עם ענפים

```
main ──●──────────●──────────────●──────────────────────●──▶
        \        / PR #1  \     / PR #2   \           / PR #3
         ●──────●  מאגר-מידע  ●──●  הדגשת-מיזוג  ●─────●  design-place-manage-eval
```

1. יוצרים ענף חדש מ-`main` לכל שינוי.
2. מריצים בדיקות מקומית: `npm run lint`, `npm test`, `npm run eval`.
3. פותחים Pull Request ל-`main`. ה-CI מריץ את כל הבדיקות אוטומטית.
4. ממזגים רק כשה-CI ירוק.
5. Railway מעלה את הגרסה החדשה.

## 5. טיפול בתקלות

| תסמין | סיבה אפשרית | פתרון |
|---|---|---|
| האתר לא נטען | השירות קרס או בבנייה | Railway, לשונית Deployments: בודקים סטטוס ויומנים. אם צריך, חוזרים לגרסה קודמת ([place.md](place.md), סעיף 6) |

| תג "מצב הדגמה" למרות שהוגדר מפתח | המפתח שגוי או חסר | בודקים את המשתנה ואת היומנים (`[ai]`) |
| המשימות נעלמו אחרי עדכון | `DATA_DIR` לא מצביע לתוך ה-Volume | מתקנים את המשתנה. נתונים שנכתבו מחוץ ל-Volume אבדו |
| המנהל לא מקבל "בוצע!" | הדף לא פתוח, או בעיית רשת | ההתראה נשמרת בשרת ותופיע בפעמון כשהדף ייפתח |
| עובד לא רואה משימה | המשימה עדיין טיוטה, או שויכה לעובד אחר | המנהל בודק את הסטטוס והשיוך |

## 6. אבטחה שוטפת

- לא להעלות את `.env.local` או את התיקייה `knowledge/` לגיטהאב (שתיהן ב-`.gitignore`).
- להחליף את מפתח ה-API אם יש חשד שנחשף.
- לבדוק מדי פעם ב-`npm audit` אם יש עדכוני אבטחה לספריות.
- כל עוד אין התחברות אמיתית, לא לשתף את הכתובת מחוץ לצוות.
