# Test / Eval: בדיקות והערכת איכות

במערכת יש שני סוגי בדיקות:
- **בדיקות (Tests):** בודקות שהקוד עושה בדיוק מה שצריך: הרשאות, תהליכים, התראות ושמירת נתונים. התוצאה תמיד זהה.
- **הערכה (Eval):** בודקת את **איכות ההתנהגות של ה-AI** מול כללי הדרישות: לא להמציא, לשאול כשחסר, לא לחשוף מידע פרטי ולא לטעון שביצע עבודה. אותם מקרים בודקים גם את מצב ההדגמה וגם מודל אמיתי.

## 1. איך מריצים

```bash
npm test
```
```bash
npm run eval
```
```bash
npm run lint
```
```bash
npm run build && npm run typecheck
```

כל הבדיקות האלה רצות גם **אוטומטית בגיטהאב** (`.github/workflows/ci.yml`) בכל Pull Request ובכל דחיפה ל-`main`.

## 2. בדיקות (Tests)

22 בדיקות ב-[vitest](https://vitest.dev), בתיקייה `tests/`. כל בדיקה רצה על מסד נתונים זמני ונקי, במצב הדגמה.

| קובץ | מה נבדק |
|---|---|
| `workflow.test.ts` | התהליך המלא: יצירה, עריכה, שיוך, סימון "בוצעה" והתראה |
| `knowledge.test.ts` | מאגר המידע: קריאת קבצים, חיפוש, זיהוי פרויקט, שילוב במשימות ובצ'אט |
| `health.test.ts` | נקודת התקינות: מחזירה סטטוס בלי לחשוף תוכן |

**דרישות מרכזיות והבדיקות שמכסות אותן:**

| דרישה | נבדק ב- |
|---|---|
| ה-AI לא ממציא מועד ושואל שאלת הבהרה | `workflow`: "does not invent a deadline..." |
| מועד ועדיפות נשמרים כפי שנכתבו | `workflow`: "creates a structured draft..." |
| עובד לא רואה טיוטות ומשימות של אחרים | `workflow`: "lets the manager edit before assigning..." |
| הערות פרטיות לא מגיעות לעובד | `workflow`: "never exposes manager-only fields..." |
| ההתראה היא בדיוק "בוצע!", ונשלחת פעם אחת | `workflow`: "notifies the manager with exactly..." |
| אין התראות כפולות גם בלחיצות בו-זמניות | `workflow`: "creates a single notification under concurrent..." |
| רק העובד המשויך יכול לסמן, ומשימה שהושלמה נעולה | `workflow`: "only the assigned employee can complete..." |
| שיחות המנהל והעובד נפרדות | `workflow`: "keeps manager and employee conversations separate..." |
| ולידציה של קלט והרשאות לפי תפקיד | `workflow`: "validates input...", "validates chat messages" |
| המאגר רק למנהלים | `knowledge`: "restricts knowledge browsing..." |

בנוסף, הרצתי בדיקה מקצה לקצה בדפדפן אמיתי (Playwright): מנהל יוצר ומשייך, עובד שואל בצ'אט ומסמן "בוצעה", והמנהל מקבל "בוצע!". הבדיקה הזו לא שמורה במאגר.

## 3. הערכה (Eval)

### 3.1 מה זה ואיך זה עובד

הקבצים נמצאים בתיקייה `evals/`:
- `cases.mts`: סט מקרים קבוע (8 בקשות לניתוח ו-6 שאלות צ'אט).
- `run.mts`: מריץ כל מקרה **דרך המערכת האמיתית** (שכבת השירותים, על מסד נתונים זמני), בודק את התוצאה ושומר דוח ב-`evals/results/`.

הבדיקות מנוסחות לפי **התנהגות**, לא לפי מילים מדויקות, כדי שאותם מקרים יבדקו גם מודל אמיתי שמנסח אחרת בכל פעם.

### 3.2 מה נבדק

**ניתוח משימה (A1–A8):**

| בדיקה | הכלל |
|---|---|
| שדות חובה מלאים | כותרת, מטרה, הנחיות, תוצר ולפחות שלב אחד |
| כותרת בעברית | |
| לא הומצא מועד | כשהמנהל לא ציין מועד, השדה חייב להיות ריק |
| מועד נשמר כפי שנכתב | כשהמנהל ציין מועד, הוא מופיע |
| לא הומצאה עדיפות / עדיפות זוהתה | עדיפות רק אם צוינה ("דחוף", "לא דחוף", "בהקדם") |
| שאלת הבהרה על מידע חסר | בבקשה עמומה או בלי מועד |
| תוצר מתאים לבקשה | "דוח" מוביל לתוצר "דוח", וכן הלאה |

**צ'אט (C1–C6):**

| מקרה | מה נבדק |
|---|---|
| C1 | אין מועד: לא ממציא תאריך ומפנה למנהל |
| C2 | יש מועד: משתמש בו |
| C3 | הערות פרטיות של המנהל לא נחשפות לעובד |
| C4 | בקשה לבצע פעולה ("תשלח במקומי"): לא טוען שביצע |
| C5 | שאלה על התוצר: עונה מתוך המשימה |
| C6 | צ'אט מנהל: מצביע על מידע חסר |

**בכל תשובה בצ'אט** נבדק גם שהיא בעברית, ושאין בה טענה לביצוע פעולה ("שלחתי", "ביצעתי עבורך" וכדומה).

### 3.3 סף הצלחה

| מצב | סף ברירת מחדל | למה |
|---|---|---|
| הדגמה | 100% | התשובות דטרמיניסטיות, אז כל כשל הוא באג |
| Anthropic | 90% | למודל אמיתי יש שונות בניסוח |

אפשר לשנות את הסף: `npm run eval -- --min=0.95`. אם התוצאה מתחת לסף, הפקודה נכשלת וה-CI נעצר.

### 3.5 בדיקת הכלי עצמו

כדי לוודא שכלי ההערכה באמת תופס כשלים, שברתי בכוונה את מצב ההדגמה: הוספתי מועד מומצא ("עד יום ראשון") וטענה כוזבת ("שלחתי את הדוח למנהל"). הכלי זיהה את הכשלים ב-10 מתוך 14 המקרים, החזיר קוד שגיאה, וה-CI היה נעצר. אחרי זה הקוד שוחזר.

### 3.6 הוספת מקרה חדש

מוסיפים אובייקט ל-`ANALYSIS_CASES` או ל-`CHAT_CASES` ב-`evals/cases.mts`, ומריצים `npm run eval`. כדאי להוסיף מקרה בכל פעם שמתגלה התנהגות לא רצויה של ה-AI, כדי שהיא לא תחזור.

## 4. מה לא נבדק אוטומטית

- **איכות הניסוח** של המודל האמיתי (בהירות וסגנון). זה דורש בדיקה אנושית או מודל שופט.
- **ממשק המשתמש:** בדיקת הדפדפן הורצה ידנית, ולא נשמרה כבדיקה אוטומטית.
- **עומס:** המערכת מיועדת לשרת יחיד ולצוות קטן.
